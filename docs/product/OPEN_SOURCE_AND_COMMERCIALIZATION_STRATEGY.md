# EgoLabs 公开研发、商业化与专利策略

## 1. 决策范围与长期方向

创始人于 2026-10-27 同意整体方向后进一步明确：专利不能成为开源的前置条件，应强调 AI 时代的快速迭代；严谨应帮助发现更优路径，不能演变为不断追加的阻碍。本次纠偏优先于同日上一轮修订中的串行审查和首发清单。本文作为开源、商业验证和知识产权管理的策略入口；商业需求、具体许可证、专利可授权性及产品能力仍按各自证据判断。

> 通过快速公开、真实反馈和持续迭代积累知识、协作与产品能力；以可靠交付获得收入，让专利作为有边界的并行工作服务于项目。

创始人随后明确公开形态：**以 EgoLabs 建立真实开源项目，先发布项目定义、愿景和路线，再在公开仓库持续实现，并允许社区通过 Issue/PR 参与。** 用户提供的 X 名称为 EgoLabs，拟用于公司和品牌，域名为 `getego.ai`；GitHub 组织已确认为 [getegoai](https://github.com/getegoai)，显示名 EgoLabs；公司和商标注册状态仍不作推定。此澄清取代此前以教学案例或精选代码切片作为首发中心的执行方案。


Ego 的长期方向是让个人拥有由自己掌控、能够持续扩展其认知与行动能力的 AI 影子。EgoLink 是接入物理世界的随身感知与交互入口。开源积累的事件、证据、权限、恢复和协作能力应能跨设备延续；具体硬件、人群、价格及收入组合允许随验证调整。本次策略不替代现行 P0 产品定义或降低发布门槛。

### 快速迭代与 AI 协作原则

- **以获得有效反馈的速度组织工作。** 默认完成当前已获授权、可逆且能产生价值的最小一步，在真实结果中迭代。等待、错失反馈和维护流程同样有成本。
- **遇阻先回到目标和必要约束。** 必要时扩大思考的上下文，从第一性原理辨别真正的依赖与沿用的假设，比较替换实现、缩小范围、拆开耦合、合成数据或先交付可用部分。思考范围可以扩大，当前执行步骤应保持小而具体。
- **严谨任务按必要性和影响匹配投入。** 只有确实阻止当前这一步的具体问题才进入前置；其余通过并行研究、后续实验或范围隔离处理。不要从“可能还有风险”无限推导新研究和新清单。
- **优先利用 AI 和工具压缩验证成本。** 并行比较方案、自动化检查、快速原型和小实验用于更早发现错误；未知如实标注，实验可以公开后继续完善。
- **识别问题时同时给出可行路径。** 协作者应说明受影响的具体范围和本轮仍能交付的增量；沿已有用户授权推进，无需反复确认。真实凭据、他人隐私和已知权利冲突在实际内容上处理，不扩大成全项目停工。

本原则适用于项目研发与公开过程，不把商业整机验收要求前移到每一次原型、文档或代码分享。

## 2. EgoLabs 的公开项目与社区协作

公开的对象是正在建设的 Ego 产品和技术项目。首批内容可以只有清楚的愿景、产品定义、路线、现状和参与方式，随后持续加入真实代码、硬件设计、测试与研发决策。完成度低不妨碍启动，明确标注已有、在做、计划中及已知问题。

GitHub 是开放部分的实际协作主线。研发过程自然沉淀在 commit、Issue、PR、ADR 和 release 中；教程、精选案例与人机对话回顾可按需要补充，不作为首发条件，也不另建一条以内容生产为目标的主线。

### 组织与仓库规划

| 拟议仓库 | 职责 | 初期边界 |
|---|---|---|
| `.github` | EgoLabs 组织主页、`getego.ai` 与各项目入口 | 使用 `profile/README.md`；只保留愿景摘要，完整定义指向 `ego` |
| `ego` | 总项目愿景、产品定义、系统关系、跨仓路线和参与入口 | 延续现有总仓库；EgoBase/Data Core 可继续在已有工作区发展 |
| `egolink` | 真实随身设备产品与研发 | 沿用现有硬件、固件、服务端、工具及文档结构，不按语言或技术层过早拆仓 |
| `egobase`，后续按需独立 | 本地中枢、长期数据与个人状态能力 | 有独立发布、接口或维护需要时再从现有工作区迁出，不为组织图先拆库 |

GitHub 组织 slug 已确认为 `getegoai`，显示名为 EgoLabs，组织入口为 [github.com/getegoai](https://github.com/getegoai)。`getego.ai` 作为拟议统一官网入口，X 用于公开进展和交流；GitHub 保存源码与研发事实。网站建设、组织命名检查、品牌注册都不是先准备项目内容的依赖。

### 日常运作

1. README/产品定义说明正在解决的问题、目标用户、当前状态和使用条件；路线区分现在、接下来与更远期。
2. 用 Issue 表达真实问题和下一步，重要设计可先讨论；从现有 backlog 中选出少量外部也能参与的工作。
3. 维护者持续提交代码，较大改动通过分支、PR 与必要检查合并；社区通过反馈、复现、文档、硬件测试、设计和代码贡献参与。
4. 重要取舍在 Issue/ADR 留下原因，阶段进展形成版本；失败、改向和未完成项保持可见。
5. 维护者负责产品方向和合并判断，社区尚未形成时照常推进，不把有人参与作为开源成功启动的前置。

**一个项目只有一条实际开发主线；公开路线描述这条主线，社区贡献进入这条主线。** 已开放模块以 GitHub 为协作主仓，内部服务可保存私有资产、历史或备份，避免同一产品长期分叉成“内部开发版”和定期筛选的公开展示版。当前源码与连续历史已公开，后续以 getegoai/ego 和 getegoai/egolink 的 GitHub `main` 为实际主线；本地原仓库保留为来源与备份，不再作为开放模块的另一条独立主线。

GitHub 的[组织主页机制](https://docs.github.com/en/organizations/collaborating-with-groups-in-organizations/customizing-your-organizations-profile)与[分支/PR 协作流程](https://docs.github.com/en/get-started/using-github/github-flow)可作为执行参考；流程按团队规模保持轻量。

## 3. 对外能力与信任声明

发布时分别标注设计目标、源码实现、模拟验证、板上观测和产品验收。每项证据说明板卡、版本、日期、条件和限制；不同设备与不同日期的结果不能拼成未经验证的当前能力。

- **隐私**：开源提供检查条件。实际数据路径、部署版本、配置、密钥控制、保留期限和删除行为仍需验证。截至本次文档核对，现有记录仍将 VPS 存储列为工程过渡，Base 私有终点未完成相应产品验收；不得声称数据已仅在设备与私有 Base 间流转。后续状态以新的验收证据更新。
- **安全**：Safety Kernel 优先是必须满足的设计要求。结果仲裁优先级不等于调度、共享资源和故障隔离已经成立；“AI 不阻断或延误安全动作”须由目标硬件上的故障注入及响应时间证据支持。PC 仿真不能替代这一证明。
- **规格**：48h 续航、重量、防水、射频、声学及认证均需对应整机证据。20g、IP68 等候选规格不得作为已实现卖点；具体目标以当前产品基线为准。
- **发布边界**：工程实验、演示与可依赖的商业产品分开。当前文档中的 P0-LOC、P0-CALL、P0-SOS 仍为 `NOT_RUN`；本次策略修订不改变其状态。免责声明不能代替产品验证和适用义务。

下层历史决策中的数字和绝对表述应按其原始范围阅读；没有独立证据时，只能作为目标或要求，不能因策略更新而获得“已实现”标签。

## 4. 开放范围与商业验证

| 内容 | 原则与边界 |
|---|---|
| 研发案例、方法、协议、模拟器、参考实现 | 默认开放，按实际增量做必要的敏感信息与来源检查；不逐项等待专利结论 |
| 基础本地运行、数据导出、权限与审计、关键安全能力 | 作为用户可掌控、可检查的公共基础逐步交付；不把必要安全和取回个人数据的能力做成付费锁 |
| 官方设备、配置安装、可靠更新、远程支持、可选托管 | 可收费，用户购买便利、可靠交付和持续维护；服务范围、实际数据路径和成本清楚 |
| 机构管理、部署集成与服务保障 | 选择一个具体场景验证；不同时把养老、高危作业和资产管理都列为开发主线 |
| 个人轨迹、联系方式、设备身份、密钥、客户与合作方保密资料 | 不进入公共仓库；合成数据、必要脱敏与授权材料另行准备 |
| 已明确保留的具体技术细节、拟保密的制造诀窍 | 仅隔离有明确范围和理由的部分，以替代实现或裁减内容维持开源进度；“可能有专利”不自动构成保留 |

定制 PCB、防水、射频与功耗首先是工程交付门槛。竞争优势需由良率、校准、返修率、支持效率、兼容性、持续体验与信任证明。硬件收入应计算完整成本，不能仅用售价减 BOM。

通信、家庭协作、远程支持等持续服务是候选收入。订阅需要持续价值、用户留存、完整交付成本以及相应运营合作条件；有月费不等于已有稳定 MRR。eSIM、应急代拨、短信及告警升级不因写入策略而成为现有能力或已获准经营范围。

开发套件、培训和标准化技术支持可作为较早的小额商业实验，但应记录人工时间、限制投入，避免课程与定制外包挤占产品研发。定价和客户群均待实际验证。

社区价值与商业价值分别评价：前者看独立复现、复用、有效反馈、贡献和维护成本；后者看持续使用、真实付款、再次付费、售后负担和单位交付成本。传播不能替代购买证据，用户个人数据也不作为公司的独占壁垒。

## 5. 许可、贡献与品牌

本次已公开的自有软件采用 Apache-2.0，原创文档及 EgoLink 自有硬件设计采用 CC BY 4.0；项目自生成规则/合成模型资产与第三方例外已按类别列明。具体授权以各仓库的 LICENSE/LICENSING 为准，本文不代替许可证或更换上游许可。后续新增硬件、模型、数据和第三方材料继续按实际来源和适用条款处理。

不默认给全部研发文档添加 NC 限制。若确有商业保留需求，应列明具体内容与理由；软件开源和文档的限制使用须分别说明，不向 Apache 许可证叠加禁止商业使用的自定义限制。[OSI 开源定义](https://opensource.org/osd)要求允许商业使用；[CC 官方说明](https://creativecommons.org/faq/#does-my-use-violate-the-noncommercial-clause-of-the-licenses)解释了 NC 的用途判断边界。

[Apache-2.0 第 3 条](https://www.apache.org/licenses/LICENSE-2.0)包含贡献者可许可、且被其贡献单独或与所提交作品结合所必然实施的专利权利要求之免费许可，以及特定专利诉讼触发的许可终止机制。它不是对公司全部专利的自动授权，也不是免遭专利诉讼的保证。不得对合规使用已授权实现的人另收覆盖范围内的专利费。

因此，本阶段专利主要服务于防御、合作和保留选择权；产品、支持及服务承担主要商业验证。若未来以独占许可或双重许可收费为核心，必须在相关实现发布和接收贡献前厘清权利控制、贡献协议与专利范围。不能假定已发出的许可可追溯撤回。

接收贡献时明确来源、贡献者有权提交的依据、入站与出站许可及署名；不能因 AI 生成而跳过第三方权利检查。品牌和“官方产品”身份单独管理，允许合规复用不等于允许冒充官方。

## 6. 开源优先，专利并行

本节是按中国为主要申请地的工作原则，尚未完成针对项目的专利检索、权利要求分析或自由实施评估；不认定任何候选已具有新颖性、创造性或商业价值。

### 6.1 默认推进与具体保留边界

开源推进不等待专利盘点、检索、交底、申请号或受理结果。专利工作从研发中发现少数有价值的机会，并行进行；不要求每项技术先证明“没有专利价值”才能公开，也不要求发布前完成全面自由实施分析。

需要暂缓的只能是已明确决定保留、能够指出具体内容和理由的技术细节，范围落实到文件、函数、图纸或段落；宽泛的技术方向和候选池不自动进入保留范围。对已知的具体披露疑点，优先用通用替代实现、可公开的接口示例、合成案例或暂不包含该细节的增量继续发布；不能解决一个疑点就暂停整个开源工作。

专利路线与发布节奏冲突时，比较保留权利的预期收益与延迟公开、学习、合作的机会成本，优先寻找解耦路径。放弃某项申请机会可以是合理的商业取舍，不以“可能申请”默认压过开源；已明确保留项目的取舍只处理该具体范围。用一条简短决策记录说明实际选择，不建立普遍审批链。

中国[专利法第 22、24 条](https://www.cnipa.gov.cn/art/2020/11/23/art_2197_155169.html)中的现有技术和法定例外不能解读为普通主动 GitHub 发布享有通用六个月宽限期。采取申请后公开时，应保存申请文件与收件信息，并核对公开内容已被申请实质覆盖；空泛占位、申请号或受理通知不等于获得专利权。新增改进另行评估，无需等待授权才开展已覆盖内容的公开。

上述法律事实用于具体取舍，不转化成全仓发布门槛。只有选择申请优先的已保留方案才安排申请覆盖核对；其余按开源迭代推进。代码、日志、图纸和演示均可能披露技术，划分保留边界时按内容判断，而非只按文件类型。

### 6.2 发明挖掘候选池

| 候选 | 进一步需要明确的技术贡献 |
|---|---|
| 跨模态自监督与伪标签 | 错误监督识别、分歧处理、不确定性传播及可比较的效果 |
| 确定性安全平面与端侧 AI 隔离 | 资源受限条件下的抢占、共享资源处理、故障恢复与有界时延机制 |
| 弱网事件同步与时序重构 | 重启、时钟漂移、乱序、重复和有限存储下的具体一致性机制 |
| 动态低功耗管理 | 在相同可靠性和时延约束下有区别的调度机制及能耗效果 |
| 模块化结构、防水声学装配 | 实际形状、构造、装配或外观的区别；性能目标本身不是技术方案 |

候选池只作研究线索，不构成公开排除清单。决定投入申请时，再按需要整理技术交底：技术问题、最接近方法、实质差异、可实施方案、效果与证据状态、替代实现、自然人发明人及权属、既往公开、拟公开日期、商业用途、申请/保密/公开建议。申请不必等量产，但须充分公开可实施的技术，不能用产品愿景替代。[现行 AI 专利审查说明](https://www.cnipa.gov.cn/art/2025/12/4/art_66_202935.html)供交底时核对。

核对共同开发、外包和职务成果的权属；优先选择极少数有业务价值且有技术依据的方案。需要海外保护时，按目标市场安排优先权与申请费用；中国完成的发明/实用新型向外申请须处理保密审查。发明/实用新型的海外优先权通常为 12 个月，PCT 不是全球专利；具体期限由经办人核对。[中国实施细则](https://www.cnipa.gov.cn/art/2023/12/21/art_3317_189352.html)、[WIPO PCT 说明](https://www.wipo.int/en/web/pct-system/faqs/faqs)。

### 6.3 防御性公开的用途与限制

不申请且决定分享的技术，可用充分说明、公开版本、公开日期证据与长期可访问记录形成现有技术材料。Git 提交日期可设置，不能单独视为权威公开时间戳；公开也不保证免于他人更早专利的约束，不能称为“不可辩驳”或“阻止任何诉讼”。[Git 日期说明](https://git-scm.com/docs/git-commit#Documentation/git-commit.txt---datedate)。
