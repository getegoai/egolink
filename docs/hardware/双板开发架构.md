双板开发架构

```text
AMOLED板（IMU、麦克风、屏幕）
        ↓ USB串口
电脑上的 PC Bridge / PC Simulator
        ↑ USB串口
4G板（SIM7670G、GNSS、摄像头）
```

电脑同时连接两个开发板，充当临时消息中继和调试中心：

* AMOLED板上传运动事件、声音事件、用户操作；
* 4G板上传定位、网络状态、照片状态；
* 电脑运行 ContextRouter，将决策分别下发给两个板；
* 所有消息、原始数据和日志都能保存、回放和分析。

这比现在直接接UART线更容易开发和排错，也符合Ego Link先完成端侧感知与协同闭环、后续再收敛到独立硬件的路线。

## 推荐当前架构

```text
ESP32-S3-Touch-AMOLED-2.06

```

## 两块板不需要直接认识对方

不要在代码中写成：

```text
AMOLED板直接控制4G板
```

应写成统一消息协议：

```text
设备 → PC事件总线 → 路由/决策 → 目标设备
```

例如：

```json
{
  "source": "wearable-node-001",
  "type": "motion_event",
  "seq": 1024,
  "timestamp_ms": 1782210408000,
  "payload": {
    "impact_score": 0.92,
    "fall_score": 0.78,
    "stationary_seconds": 12
  }
}
```

电脑判断后向AMOLED板发送：

```json
{
  "target": "wearable-node-001",
  "type": "ask_user",
  "payload": {
    "text": "检测到异常撞击，你现在安全吗？"
  }
}
```

同时向4G板发送：

```json
{
  "target": "connectivity-node-001",
  "type": "request_location"
}
```

## 初期连接方式

两块板分别插入电脑USB口，一般会出现两个COM端口，例如：

```text
COM7  AMOLED板
COM9  SIM7670G板
```

但程序不要永久依赖COM编号，因为重新插拔后编号可能改变。每块板启动后先发送：

```json
{
  "type": "hello",
  "device_id": "wearable-node-001",
  "role": "wearable_node",
  "protocol_version": "0.1"
}
```

PC Bridge根据`device_id`和`role`识别板子，而不是根据COM7或COM9识别。

## 原始音频要注意

普通115200波特率实际有效吞吐约10KB/s左右，而16kHz、16位、单声道原始音频约为：

```text
16000 × 2字节 = 32KB/s
```

因此115200串口不能稳定持续传输原始音频。

当前建议：

* IMU原始数据可以通过串口发送；
* 音频优先在AMOLED板本地保存到TF卡，或只发送AudioGate结果；
* 需要传短音频时使用USB CDC高波特率、Wi-Fi或文件导出；
* 不要持续把麦克风原始流通过普通UART发送。

## 这种方式的优势

* 无需接线，避免GPIO冲突和电气问题；
* 两块板可以独立烧录和重启；
* 可以同时查看两个串口日志；
* 便于记录真实IMU、声音、GNSS和事件数据；
* PC可以模拟未来Ego Base；
* 可以快速修改ContextRouter，不必每次烧录设备；
* 非常适合模型训练前的数据采集与回放。

## 它不能替代最终板间验证

电脑中继模式暂时无法验证：

* 两块板脱离电脑后的自主协同；
* 板间UART实际可靠性；
* 独立设备启动顺序；
* 断线重连；
* 实际端到端时延；
* 整机待机功耗；
* 电脑不存在时的安全兜底。

因此开发顺序建议是：

```text
阶段1：双板分别连电脑
完成数据采集、协议和安全闭环

阶段2：电脑仍参与，但ContextRouter逐渐迁到4G板
验证端侧决策

阶段3：两板UART直连
电脑只看日志，不参与业务

阶段4：脱离电脑独立运行
验证弱网、重启、功耗和安全兜底

阶段5：合并为自定义单主板
```

当前完全可以先不接UART。甚至在MotionNet和AudioGate真实模型尚未完成前，**双板接电脑是最有效率的开发模式**。

## HDBRIDGE-002 落地状态

2026-06-23 已在 ESP32-S3-Touch-AMOLED-2.06 上加入最小 AMOLED bridge 固件：

* `firmware/amoled_bridge/`

实测结果：

* Windows 识别 AMOLED 板为 ESP32-S3 native USB `COM9`，VID/PID 为 `303A:1001`；
* `idf.py -p COM9 flash` 成功，识别 ESP32-S3、PSRAM 8MB、MAC `02:00:00:00:00:01`；
* USB JSONL 捕获 43 行：`hello`、`imu_whoami`、40 条 `imu_sample`、`amoled_bridge_done`；
* AXP2101 chip id 为 `0x4A`；
* QMI8658 WHOAMI 为 `0x05`；
* 样本窗口 `samples_emitted=40`、`read_errors=0`、`not_ready_count=0`；
* PC Bridge 存储 43 条事件，session recorder 生成 40 条 `imu_motion` frame；
* quality gate PASS，`quality_score=0.94`；
* replay PASS，40 条输入均为 `risk_type=none`。

边界仍然明确：HDBRIDGE-002 只证明 QMI8658 身份和短窗口样本可进入 PC Bridge/M1 闭环。它不证明 ODR、抖动、丢帧、安装方向、校准、FIFO/中断、麦克风、屏幕触摸、TF/SD、功耗或两板 UART 已验收。AMOLED IMU 数据仍必须标记为 `source_availability=bridge_uplink`、`source_status=unverified`。
