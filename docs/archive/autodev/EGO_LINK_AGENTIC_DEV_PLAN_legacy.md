# Ego Link P0 渐进式智能体开发方案

> 本文档与 `EGO_LINK_P0_CONTEXT.md` 配套使用。目标是减少 Codex 长时间无边界推理、重复尝试和上下文漂移，同时不引入复杂多智能体框架。

## 1. 结论

Ego Link P0 有必要采用“智能体化开发流程”，但当前不应建设复杂多智能体系统。

第一阶段采用：

- 人：产品负责人、任务拆分者、最终验收者；
- Codex：单一实现智能体；
- Markdown 文件：持久化项目规则、当前任务和状态；
- 自动化测试：独立验证器；
- Git：检查点和回滚机制。

当前不引入：

- Agents SDK；
- MCP 编排；
- LangGraph、AutoGen、CrewAI 等框架；
- 自动递归分解任务；
- 并行子智能体；
- 自动合并多个分支；
- 无终止条件的长任务。

核心原则：先把“一个智能体稳定完成一个小任务”做好，再增加第二个角色。

---

## 2. Codex 长时间 thinking 的主要工程原因

Codex 长时间运行通常不是因为缺少更多智能体，而是因为任务契约不完整：

1. 一个提示中包含多个目标；
2. 没有明确“不做什么”；
3. 没有可执行的完成条件；
4. 缺少确定性的构建和测试命令；
5. 允许无限修复循环；
6. 读取过多项目材料，持续扩大上下文；
7. 执行了不会自动退出的命令，例如串口监视、开发服务器、持续日志或 watch；
8. 任务被允许顺带重构、补文档、优化架构和处理未来功能。

因此，当前先解决边界、验证和停止机制，不靠增加智能体解决。

## 3. Stage 0：单智能体受控开发（现在执行）

### 3.1 角色

```text
用户
├─ 决定本次任务
├─ 审核任务边界
└─ 验收结果

Codex Builder
├─ 读取固定上下文
├─ 只实现 CURRENT_TASK
├─ 运行指定验证
├─ 更新状态
└─ 达到完成或阻塞条件后停止

测试脚本
└─ 给出独立、确定性的通过/失败结果
```

### 3.2 每次运行只读取

1. `AGENTS.md`；
2. `EGO_LINK_P0_CONTEXT.md`；
3. `tasks/CURRENT_TASK.md`；
4. 当前任务明确列出的源文件。

不要默认遍历全部仓库、历史文档、采购资料或未来路线文档。

### 3.3 每次运行只做一个目标

一个任务应控制在 15～45 分钟的正常执行范围内，示例：

- 建立 ESP-IDF 最小可编译工程；
- 定义事件 JSON 数据结构并完成单元测试；
- 实现 Wi-Fi 连接；
- 实现 MQTT 心跳；
- 实现串口 `wake` 命令；
- 实现 Mock GNSS 单次定位上报；
- 实现离线队列入队；
- 实现重连后的顺序补传。

下列组合不应作为一个任务：

- “完成全部固件和 PC Simulator”；
- “实现 MQTT、策略、离线缓存、Dashboard 和真实 4G”；
- “全面检查项目并把能改的都改好”。

### 3.4 强制停止契约

Codex 必须在以下任一条件满足时结束本轮：

- `Done when` 全部满足；
- 同一个验证命令连续修复 2 次仍失败；
- 缺少硬件、SDK、凭据、串口设备或外部依赖；
- 需要修改 `Allowed paths` 之外的文件；
- 发现任务规格互相矛盾；
- 需要引入新生产依赖；
- 需要改变已有架构决定；
- 当前问题无法通过现有日志复现。

阻塞时不得继续猜测。应在 `STATUS.md` 中记录：

- 阻塞点；
- 已验证的事实；
- 最近一次错误；
- 建议的下一步；
- 未完成内容。

### 3.5 命令约束

禁止默认运行不会自行退出的命令，例如：

- `idf.py monitor`；
- `tail -f`；
- 无退出条件的本地服务；
- `watch`；
- 无限串口读取；
- 持续等待网络或硬件响应。

需要服务时，应由用户单独启动，或通过可控测试脚本启动、验证后自动关闭。

### 3.6 推理级别

日常 P0 任务使用中等推理强度。只有协议重构、难以复现的并发错误、底层驱动设计等任务，才临时提高推理强度。

## 4. 最小文件体系

仓库根目录仅增加以下控制文件：

```text
ego-link-p0/
├─ AGENTS.md
├─ EGO_LINK_P0_CONTEXT.md
├─ STATUS.md
├─ tasks/
│  ├─ CURRENT_TASK.md
│  └─ TASK_TEMPLATE.md
└─ scripts/
   └─ verify.ps1          # 项目形成稳定验证命令后再加入
```

### 文件职责

- `AGENTS.md`：始终生效的短规则，控制在约 100 行以内；
- `EGO_LINK_P0_CONTEXT.md`：产品边界、硬件、架构和阶段目标；
- `CURRENT_TASK.md`：本轮唯一工作合同；
- `STATUS.md`：当前事实、最近验证结果和阻塞；
- `verify.ps1`：统一构建和测试入口，后续逐步完善。

不要把完整项目背景全部复制进 `AGENTS.md`。

---

## 5. 标准执行流程

```text
1. 用户选择一个任务
2. 填写 tasks/CURRENT_TASK.md
3. 新开一个 Codex 线程
4. Codex 读取 AGENTS.md、P0 Context、CURRENT_TASK
5. Codex检查仓库与任务前提
6. Codex写最多 5 行执行计划，不等待确认，立即实施
7. Codex运行指定验证命令
8. 通过：更新 STATUS.md，停止
9. 阻塞：更新 STATUS.md，停止
10. 用户查看 diff 和验证结果
11. Git commit
12. 再创建下一个任务
```

原则：一个任务一个线程、一个任务一个提交。不要在同一长对话中连续追加多个独立任务。

## 6. P0 推荐任务序列

### T001：工程基线

- ESP-IDF 工程可执行 `idf.py build`；
- PC Simulator Python 环境可启动最小健康检查；
- 不实现业务功能。

### T002：协议模型

- 定义 status、event、command、ack 的 JSON 字段；
- 提供序列化/反序列化测试；
- 不接 MQTT。

### T003：Wi-Fi 链路

- ESP32-S3 连接指定 Wi-Fi；
- 输出明确状态；
- 失败后有限次数重试；
- 不接 SIM7670G。

### T004：MQTT 心跳

- 连接电脑 MQTT Broker；
- 每 10 秒发布一次 status；
- PC 能记录消息；
- 不做定位和策略。

### T005：串口 CLI 与模拟事件

- 支持 `status`、`wake`、`sos`；
- 生成统一事件结构；
- 不实现真实唤醒和拨号。

### T006：Mock GNSS

- 支持固定点和预设轨迹；
- `loc` 命令触发定位上报；
- 不调用 SIM7670G GNSS。

### T007：离线队列

- 网络断开时事件入队；
- 队列有容量和溢出策略；
- 不做恢复补传。

### T008：恢复补传

- 重连后按 `seq` 顺序补传；
- PC 端去重；
- 有可重复测试。

### T009：命令与策略下发

- 接收 `request_location`、`play_prompt`、`set_policy`；
- 返回 ack；
- 只实现 P0 策略字段。

### T010：P0 集成验收

- 心跳；
- 模拟定位；
- wake；
- SOS；
- 网络中断；
- 恢复补传；
- PC 下发命令；
- 全流程产生可检查日志。

---

### T011：摄像头拍照 Smoke Test

- 打开 ESP32-S3 摄像头；
- 采集一张 JPEG 照片；
- 通过串口日志输出照片大小、格式和校验值；
- 可选通过 Wi-Fi HTTP `/capture` 查看照片；
- 不接入 P0 主业务事件闭环，不做持续视频流。

## 7. Stage 1：增加第二角色，但不并行（满足条件后）

进入条件：

- 已连续完成至少 5 个小任务；
- 每个任务都有确定性验证；
- `AGENTS.md` 基本稳定；
- Codex 不再经常无边界运行；
- 协议与目录结构已稳定。

增加一个只读 Reviewer：

```text
Builder
├─ 实现 CURRENT_TASK
└─ 提交 diff 与验证结果

Reviewer
├─ 不改代码
├─ 只检查当前 diff
├─ 检查任务是否越界
├─ 检查错误处理和测试缺口
└─ 输出最多 5 条问题
```

Reviewer 可用另一个 Codex 线程或内置子智能体，但必须串行：Builder 完成后再审查。当前不要让两个角色同时改代码。

---

## 8. Stage 2：按领域拆分智能体（接口稳定后）

进入条件：

- 固件与 PC Simulator 都有自动测试；
- MQTT 协议已经冻结为版本化规范；
- Git 分支和合并流程稳定；
- 任务之间依赖关系清楚。

可以形成三个角色：

```text
Firmware Agent
└─ 只修改 firmware/

PC Simulator Agent
└─ 只修改 pc_simulator/

Integration Reviewer
└─ 只读检查协议兼容、集成测试和验收结果
```

此阶段才考虑使用独立 worktree 或 Codex 内置子智能体。每个智能体必须限定目录，不能共同修改协议文件。

协议修改应作为独立任务，由用户批准后先更新 `docs/protocol.md`，再分别派生固件和 PC 端任务。

---

## 9. Stage 3：轻量自动编排（以后再做）

只有任务格式、验证命令和停止条件长期稳定后，才增加一个简单的 PowerShell/Python 脚本：

```text
读取 CURRENT_TASK
→ 调用 codex exec
→ 设置外部超时
→ 收集最终结果
→ 运行 verify.ps1
→ 保存日志
→ 成功则等待人工审核
→ 失败或超时则标记 BLOCKED
```

编排器只负责启动、超时、记录和状态转换，不让它自动拆分无限任务，也不允许智能体递归生成智能体。

---

## 10. 何时才需要 Skill、MCP 或更复杂框架

### Skill

同一套操作稳定重复 3 次以上，例如：

- 创建 ESP-IDF 组件；
- 增加 MQTT 消息类型；
- 运行 P0 集成验收；
- 审查离线队列可靠性。

此时可将流程封装为 Skill。

### MCP

只有 Codex 必须访问项目外系统时才引入，例如：

- 读取真实硬件测试平台；
- 查询设备日志服务；
- 操作任务管理系统。

当前 P0 不需要 MCP。

### 多智能体框架

只有出现稳定、可并行、边界清晰且人工调度成本明显过高的任务，才评估更复杂框架。Ego Link P0 当前不满足这一条件。

---

## 11. 当前建议

立刻采用 Stage 0：

1. 使用仓库根目录 `AGENTS.md`；
2. 保留现有 `EGO_LINK_P0_CONTEXT.md`；
3. 每次只填写一个 `CURRENT_TASK.md`；
4. 使用新线程执行；
5. 默认中等推理；
6. 最多两轮修复；
7. 不运行常驻命令；
8. 完成或阻塞都必须停止；
9. 每个任务独立 Git commit；
10. 完成 5 个稳定任务后，再增加只读 Reviewer。

这已经是一套有效的智能体开发系统，但没有引入额外框架，也不会过早承担多智能体编排复杂度。
