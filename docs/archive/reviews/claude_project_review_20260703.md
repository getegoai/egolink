# EgoLink 项目文档 Review 报告

基于对全部 docs/ 目录（约 120+ 文件）、根目录三篇中文研讨记录、AGENTS.md 体系和 autodev 运行记录的完整阅读，整理出以下发现。

## 项目现状速览

EgoLink P0 是"AI 主动守护定位器"验证项目，目标场景是跌倒/异常检测→用户确认→位置证据→安全事件闭环。当前处于 **KR-007 已发布（2026-07-02，reconnect store-forward）、KR-008 产品演示闭环候选阶段**：定位融合算法 EALE-P0（规则+可解释证据，非黑盒模型）已设计冻结，Safety Companion 模型 M0 契约完成、M1 数据基础执行中约 50%，71 个任务已完成但**电池续航、隐私合规、APP/移动端、真实场景 GNSS 验收几乎是空白**。

---

## 一、架构与技术路线（产品/系统架构）

**关键发现**：架构分层清晰（USB-Free/VPS Message Hub、双板 PC Bridge、四层平台可迁移性），但硬件能力的"单一真值源"缺失——固件、PC Simulator、Replay 对同一传感器（IMU/摄像头/麦克风）的可用性默认值不一致，Safety 模型可能请求实际不存在的证据。量产主控（ESP32-S3 vs STM32U5A5 vs Apollo4）、蜂窝模组、双板直连方案均未冻结。

**审查问题**：
1. 是否应让固件通过 `hello` 消息显式上报真实硬件能力（单一真值源），而非应用层各处声明？
2. ADR-0001 规定"验收必须走 VPS 路径"，但当前 P0-A/B 验收仍以双板 USB+PC 为准——这个矛盾何时消解？
3. P1 阶段计划把 MotionNet/AudioGate 下沉到 AMOLED 板独立运行，但尚无模型体积、量化策略、推理延迟/内存预算评估——这决定了单芯片方案是否可行，是否该在 P1 前补一次"footprint 评估"？
4. 功耗选型闸门（48-72h 续航）目前完全没有可测量的基准定义（轻度使用 vs 守护模式续航应分开度量）。
5. ESP32-S3 / STM32U5A5 / Apollo4 三个候选平台缺少报价、MOQ、交期、FAE 支持的对标表格，量产 BOM 决策依据在哪里？
6. SIM7670G 是否真能满足中国三网认证要求，还是仅"够用于 P0 功能验证"？
7. "PC 不是产品依赖"的原则如何在验收门中被实质性检验，而不只是文档声明？

## 二、任务规划与进度

**关键发现**：任务前缀分类（LTE/FW/LOC/OBS/ALG/DEMO/REL 等）体系清晰，Task Packet 结构规范。但已完成 71 个任务里，**LTE(11)、REL(11)、FW(8) 投入最重，电池/隐私/APP/UX 几乎零任务**。autodev/backlog.json 与 LIVE_STATUS 已停滞在 2026-06-20，落后实际进度 13 天，控制平面自动化与真实开发节奏脱节。仓库无 Git remote，大量文档变更未提交。

**审查问题**：
1. LTE-001A/B、LTE-002/003 每个 fix 都单独建任务，是否让"调试迭代"掩盖了"真实决策点"，任务粒度需要重新分层（稳定功能 vs 调试注记）？
2. KR-008（产品演示闭环）的发布前置条件（location_belief 脱离 Unknown、模型训练就绪）目前没有明确日期或责任任务，何时会被规划进 active？
3. 电池/续航（R3.1）、外壳/GNSS（R3.2）在 ROADMAP 中被提及，但没有对应 `PWR-*`/`ENCL-*` 任务前缀——是遗漏还是有意延后？
4. 隐私合规边界（Wi-Fi/IMU/audio 数据处理）完全没有任务追踪，产品演示是否需要先补齐？
5. autodev backlog 与实际路线图完全脱节，这套自动化任务队列是否已经名存实亡，要不要正式废弃或重新对齐？
6. STATUS.md 上千行详细部署记录 vs 缺少"为什么走这条路""对标竞品""用户验证"的战略性文档——进度记录是否过度、方向性判断是否不足？
7. LTE-003 长期处于 paused 状态但未 closed，其依赖关系和后续任务是否需要显式了结？

## 三、定位与 Safety Companion 技术路线

**关键发现**：EALE-P0 是**规则+概率驱动、显式拒绝黑盒模型**的可解释融合框架，GNSS 主导、Cell 仅辅助（明令禁止 cell-only 坐标推算）、Wi-Fi 做已知地点匹配、IMU 只判断静止/移动。这与两篇中文研讨记录（融合算法模型研讨.md、定位技术研讨.md）方向一致，但**研讨中提出的 L0-L4 省电状态机（GNSS 按需唤醒策略）并未被 LOCATION_ENGINE.md 采纳**，是个实质性缺口。Safety Companion 侧，M0 规则基线和契约已交付，M1 数据基础执行到一半，卡点在于 **IMU 产品化验收（安装方向/FIFO/校准/功耗）未通过**，直接挡住了 MotionNet 训练启动。

**审查问题**：
1. GNSS Fine 状态 25m 半径（hdop×8）、Known-place Coarse 50m 等阈值是工程默认值还是有真实数据支撑？
2. 研讨文档提出的 L0-L4 省电状态机为何未落地到冻结设计，是否应补一个任务显式采纳或明确否决？
3. 可解释性要求（每个输出都要 evidence_refs+reason）对未来学习模型能力上限的制约有多大？ALG-003 把学习模型限制在"预测证据可信度"而非直接输出位置，这个边界是否足够灵活？
4. Wi-Fi known-place 记忆没有遗忘/过期机制——用户搬家、指纹库老化、"幽灵地点"误判如何解决？
5. MotionNet 从 IMU 数据采集（TIMU-009C-B2 的 600 样本窗）到可训练模型之间的鸿沟有多大？受限于伦理不能采集真实伤害样本，软垫模拟样本的有效性如何评估？
6. 用户标注（安全/需要帮助/误报）本身的可信度如何保证，是否需要多标注者复核或金标准校准？
7. Safety Companion 12 个确定性场景是否覆盖儿童/老人/骑行者等不同人群的运动特征差异？
8. IMU 从开发板 QMI8658 迁移到量产传感器后，MotionNet 训练数据分布是否需要重新采集？

## 四、开发流程与硬件验证

**关键发现**：AutoDev + Dual Codex Workflow（Account A 规划/Account B 独立 worktree 构建）框架完整但执行不够一致，`上下文重构.md` 提出的四层文档体系（稳定规则/当前事实/领域知识/历史证据）"蓝图已定、部分落地"，docs/ 根层仍混有本应归档的文件。硬件验证已覆盖摄像头(OV5640)、IMU(QMI8658)、4G上行、双板桥接的冒烟级验证，但**电源/续航是完全的空白——没有任何长时（>2h）实测数据、PPK2 曲线**，这对"随身安全定位器"是被低估的关键风险；GNSS 也仅验证了室内 no-fix，真实定位精度和城市峡谷场景未测。

**审查问题**：
1. Task Packet 的 `allowed_paths` 约束是否有 CI/pre-commit 强制校验，还是仅靠文档自觉遵守？
2. 从 P0 评估板到量产硬件选型的决策时间点和验收标准（功耗/成本/尺寸）在哪里，迁移会推翻多少现有验证工作？
3. 硬件验证证据（TIMU-009C、HDBRIDGE-002 等）没有版本化机制，硬件小版本升级后旧证据能否复用还是要全量重验？
4. VPS Message Hub 本身的 SLA、降级策略、存储上限在哪个文档定义？R0-R4 全通过是否等于产品就绪？
5. 电源与续航验证何时进入关键路径——当前固件是否已实现功耗状态进入/退出时间戳这类 telemetry？
6. Dual Codex Workflow 里 Account A 对 Account B 提交的"再验证清单"是否标准化，还是每次临场判断？

## 建议的 REVIEW 方案

建议按下面顺序组织一次结构化 review，每步都有明确产出物，避免陷入"文档很全但决策悬空"的状态：

**阶段 1：真值收敛（1-2天）**
- 核对硬件能力单一真值源问题（架构问题1）、清理 docs/ 根层冗余文档、给 STATUS.md/KEY_RELEASES.md/ACTIVE_BUILD.md 明确谁是权威、谁被谁引用。
- 产出：一份"当前唯一可信状态"页面 + 待删除/待归并文档清单。

**阶段 2：风险闸门优先级排序（半天）**
- 把"电池续航零实测""GNSS真实精度未测""IMU产品化验收未过""隐私合规无任务"这四项列为 P0 风险，逐一分配任务前缀（如 PWR-*、ENCL-*、PRIVACY-*）并排入 active。
- 产出：风险清单 + 对应 task packet 草稿。

**阶段 3：技术路线对齐会（1次会议）**
- 针对 L0-L4 省电状态机是否采纳、MotionNet 训练数据门槛、KR-008 发布前置条件这三个悬而未决点做出明确决策（采纳/否决/延后+理由），而不是让研讨文档和冻结设计长期并存不一致。
- 产出：ADR 或决策记录，更新 LOCATION_ENGINE.md / NEXT_STEP_M1_DATA_FOUNDATION.md。

**阶段 4：进度机制校准（半天）**
- 决定 autodev backlog 是废弃还是重新接入真实路线图；给 KR-008 设一个可检验的完成定义和大致时间预期；把"调试迭代类任务"和"里程碑类任务"在命名或状态字段上区分开。

**阶段 5：硬件量产决策前置研究（视资源而定，1-2周）**
- 对 ESP32-S3/STM32U5A5/Apollo4 做报价、MOQ、认证对标；补一次至少 24h 的真实功耗曲线测量（哪怕先用开发板+PPK2）。
